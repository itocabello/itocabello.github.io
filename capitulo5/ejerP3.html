Ejercicio resuelto 3: Ingesta de datos mediante Apache Flume utilizando Avro

En este ejercicio se propone implementar un flujo de ingesta de datos donde Apache Flume utiliza el formato Apache Avro para serializar los eventos mientras son transferidos entre diferentes componentes del ecosistema Big Data hasta su almacenamiento final en Hadoop HDFS.

El objetivo es que el estudiante comprenda cómo Avro permite representar los datos de forma eficiente y compacta, reduciendo el tamaño de la información que debe ser transmitida entre los diferentes elementos de una arquitectura distribuida.

Para ello se establece un agente Flume encargado de examinar el directorio local que contiene el fichero TABLA_ACCIDENTES_24.csv. Cuando el fichero es detectado, una Source de tipo spooldir procesa su contenido y lo transforma en una secuencia de eventos Flume.

Los eventos generados se almacenan temporalmente en un Channel de tipo memory. Posteriormente, un Sink de tipo Avro transmite los eventos al segundo agente Flume mediante el protocolo Avro.

El segundo agente recibe los eventos mediante una Source Avro, los almacena temporalmente en otro Channel y finalmente utiliza un Sink HDFS para escribir la información en el sistema de archivos distribuido de Hadoop.

Objetivo del ejercicio

El objetivo es implementar y comprender un flujo de ingesta distribuida mediante dos agentes Apache Flume conectados mediante el protocolo Avro y utilizar HDFS como destino final de los datos.

  • Configurar una Source de tipo spooldir.
  • Procesar el fichero TABLA_ACCIDENTES_24.csv.
  • Utilizar un Channel de tipo memory.
  • Configurar un Sink de tipo Avro.
  • Transmitir los eventos entre dos agentes Flume.
  • Utilizar el puerto 41414 para la comunicación mediante Avro.
  • Recibir los eventos mediante una Source de tipo Avro.
  • Almacenar los datos recibidos en HDFS.
  • Comprobar la correcta ingesta del fichero en Hadoop.

1. Arquitectura del flujo de ingesta

La solución propuesta utiliza dos agentes Apache Flume conectados mediante el protocolo Avro. El primer agente se encarga de detectar y procesar los ficheros que aparecen en el directorio de entrada, mientras que el segundo recibe los eventos y los almacena finalmente en HDFS.

El flujo completo de información puede representarse de la siguiente forma:

Agente Flume 1: Source Spooldir → Channel Memory → Sink Avro
Comunicación: Protocolo Avro mediante el puerto 41414
Agente Flume 2: Source Avro → Channel Memory → Sink HDFS

Figura 42. Arquitectura del flujo de ingesta mediante dos agentes Apache Flume conectados mediante el protocolo Avro. Fuente: elaboración propia.

De esta forma, el primer agente actúa como punto de entrada de los datos y el segundo como punto de recepción y almacenamiento. Esta arquitectura permite separar las funciones de captura, transmisión y almacenamiento de la información.

2. Configuración del directorio de entrada

El primer agente Flume utiliza una Source de tipo spooldir. Esta Source supervisa un directorio determinado y detecta automáticamente los nuevos ficheros que se incorporan al mismo.

En este ejercicio se utiliza el directorio:

/home/hadoop/flume_input

En dicho directorio se deposita el fichero:

TABLA_ACCIDENTES_24.csv

Una vez detectado el fichero, Flume lo procesa y genera eventos que serán enviados al Channel configurado para el agente.

3. Configuración del primer agente Flume

El primer agente está formado por tres componentes principales: una Source de tipo spooldir, un Channel de memoria y un Sink de tipo Avro.

La Source se encarga de detectar los nuevos ficheros, mientras que el Channel almacena temporalmente los eventos hasta que el Sink pueda procesarlos.

# Source
agent1.sources = source1
agent1.sources.source1.type = spooldir
agent1.sources.source1.spoolDir = /home/hadoop/flume_input

# Channel
agent1.channels = channel1
agent1.channels.channel1.type = memory

# Sink Avro
agent1.sinks = sink1
agent1.sinks.sink1.type = avro
agent1.sinks.sink1.hostname = agent2
agent1.sinks.sink1.port = 41414

Figura 43. Configuración del primer agente Flume encargado de capturar los datos y transmitirlos mediante Avro. Fuente: elaboración propia.

El parámetro spoolDir determina el directorio que será supervisado por la Source. El Sink de tipo avro establece como destino el segundo agente y utiliza el puerto 41414 para realizar la comunicación.

4. Procesamiento mediante el Channel de memoria

Una vez que la Source detecta el fichero TABLA_ACCIDENTES_24.csv, su contenido se transforma en eventos Flume.

Estos eventos son almacenados temporalmente en un Channel de tipo memory. Este componente actúa como mecanismo intermedio entre la Source y el Sink, permitiendo desacoplar temporalmente la velocidad de generación de eventos de la velocidad de transmisión.

Flujo interno: Fichero CSV → Source Spooldir → Eventos Flume → Channel Memory → Sink Avro

El uso de un Channel de memoria proporciona un mecanismo sencillo y rápido para el intercambio temporal de eventos. No obstante, al tratarse de almacenamiento en memoria, los eventos podrían perderse ante una interrupción del proceso antes de ser enviados al siguiente componente.

5. Transmisión de los eventos mediante Avro

El Sink del primer agente utiliza el tipo Avro para transmitir los eventos generados hacia el segundo agente Flume.

La comunicación se establece mediante el puerto 41414. De esta manera, los eventos salen del primer agente y son enviados al proceso Flume encargado de recibirlos.

agent1.sinks.sink1.type = avro
agent1.sinks.sink1.hostname = agent2
agent1.sinks.sink1.port = 41414

En este punto del flujo, Avro permite realizar la serialización de los eventos utilizando una representación binaria, evitando depender exclusivamente de una representación textual de los datos durante la comunicación.

Comunicación entre agentes: Agente Flume 1 → Sink Avro → Puerto 41414 → Source Avro → Agente Flume 2

6. Configuración del segundo agente Flume

El segundo agente Flume actúa como receptor de los eventos enviados por el primer agente. Para ello dispone de una Source de tipo Avro configurada para escuchar en el puerto 41414.

# Source Avro
agent2.sources = source2
agent2.sources.source2.type = avro
agent2.sources.source2.bind = 0.0.0.0
agent2.sources.source2.port = 41414

# Channel
agent2.channels = channel2
agent2.channels.channel2.type = memory

# Sink HDFS
agent2.sinks = sink2
agent2.sinks.sink2.type = hdfs
agent2.sinks.sink2.hdfs.path = /datasets/accidentes24

Figura 44. Configuración del segundo agente Flume encargado de recibir los eventos mediante Avro y almacenarlos en HDFS. Fuente: elaboración propia.

Los eventos recibidos por la Source Avro se almacenan temporalmente en el segundo Channel de memoria y posteriormente son recogidos por el Sink HDFS para su almacenamiento definitivo.

7. Almacenamiento de los datos en HDFS

El último componente del flujo es el Sink HDFS. Su función es recoger los eventos almacenados en el Channel y escribirlos en el sistema de archivos distribuido de Hadoop.

En este ejercicio se utiliza como directorio de destino:

/datasets/accidentes24

Una vez finalizada la transferencia, los datos quedan disponibles en HDFS para su posterior procesamiento mediante diferentes herramientas del ecosistema Hadoop.

Destino final: Agente Flume 2 → Sink HDFS → HDFS → /datasets/accidentes24

8. Comprobación de la ingesta en HDFS

Una vez ejecutados los dos agentes Flume y procesado el fichero de entrada, se puede comprobar que la información ha sido almacenada correctamente en HDFS utilizando los comandos de administración del sistema de archivos de Hadoop.

hdfs dfs -ls /datasets/accidentes24

También es posible consultar el contenido almacenado utilizando:

hdfs dfs -cat /datasets/accidentes24/*

Estas operaciones permiten verificar que el flujo de ingesta se ha completado correctamente y que los datos procedentes del fichero CSV se encuentran disponibles en HDFS.

Flujo completo de los datos

El proceso completo puede resumirse mediante la siguiente cadena de componentes:

1. El fichero TABLA_ACCIDENTES_24.csv se deposita en /home/hadoop/flume_input.
2. La Source spooldir del primer agente detecta el fichero.
3. El contenido se transforma en eventos Flume.
4. Los eventos se almacenan temporalmente en un Channel memory.
5. El Sink Avro transmite los eventos al segundo agente mediante el puerto 41414.
6. La Source Avro del segundo agente recibe los eventos.
7. Los eventos recibidos se almacenan temporalmente en otro Channel memory.
8. El Sink HDFS almacena finalmente los datos en /datasets/accidentes24.

Ventajas del uso de Avro en la comunicación

La utilización de Avro en este flujo permite introducir un mecanismo de serialización adecuado para arquitecturas distribuidas. La representación binaria facilita el intercambio de información entre procesos y permite reducir el tamaño de los datos transmitidos.

  • Utiliza una representación binaria compacta.
  • Facilita la comunicación entre diferentes procesos.
  • Permite serializar y deserializar los eventos.
  • Reduce la cantidad de información transmitida frente a determinados formatos textuales.
  • Está especialmente orientado a entornos distribuidos y aplicaciones Big Data.

Resultado del ejercicio

Al finalizar el ejercicio se ha implementado un flujo completo de ingesta de datos mediante Apache Flume, utilizando Avro como mecanismo de comunicación entre dos agentes.

El primer agente captura el fichero TABLA_ACCIDENTES_24.csv mediante una Source spooldir, almacena temporalmente los eventos en un Channel de memoria y los transmite mediante un Sink Avro.

El segundo agente recibe los eventos mediante una Source Avro, los almacena temporalmente en otro Channel y finalmente utiliza un Sink HDFS para escribir los datos en:

/datasets/accidentes24

De este modo, el ejercicio permite comprobar de forma práctica cómo puede construirse una arquitectura de ingesta distribuida utilizando varios agentes Flume y cómo Avro facilita la serialización y transmisión eficiente de los eventos entre diferentes componentes del ecosistema Hadoop.
